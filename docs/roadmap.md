# Roadmap: система составления расписания колледжа

Статус: `0.2 alpha`; семилистовый импорт учебных планов и студентов готов, импорт аудиторий и Windows-поставка запланированы.

## Принципы поставки

- Разрабатываем вертикальными срезами: каждый этап дает проверяемый пользовательский результат.
- Нормативные ограничения отделяем от локальных правил колледжа и критериев качества.
- Импорт сначала проверяет файл целиком и только затем разрешает сохранение данных.
- Автоматический расчет не заменяет ручной редактор: пользователь видит причины конфликтов и может зафиксировать занятия.
- Реальные персональные данные не включаются в репозиторий, тесты и примеры.
- Каждая сущность обновляется по стабильному коду; ФИО и название используются только для отображения и предупреждений.
- Windows-релиз считается готовым только после проверки установщика, обновления и восстановления данных на чистой системе.
- Целевой рабочий процесс формируется по нормативным требованиям, пользовательским сценариям и [функциональному benchmark](research/timetable-functional-benchmark.md); реализация остается независимой и проверяемой согласно [ADR-002](decisions/002-independent-functional-design.md).

## Этап 0. Основа проекта

Результат: воспроизводимый Python-проект с доменной моделью, тестами и командой проверки входных данных.

### 0.1. Каркас приложения

- Файлы: `pyproject.toml`, `src/rasp/__init__.py`, `.gitignore`.
- Зависимости: Python 3.12, Pydantic 2, openpyxl 3.1.
- Приемка: пакет импортируется из `src`, тесты запускаются одной командой.
- Проверка: `python -m unittest discover -s tests -v`.

### 0.2. Домен первого среза

- Файлы: `src/rasp/domain/models.py`, `src/rasp/imports/excel.py`, `tests/test_excel_import.py`.
- Приемка: типизированы преподаватель, группа и строка нагрузки; неизвестные поля и недопустимые значения отклоняются.
- Проверка: модульные тесты моделей и преобразования строк.

### 0.3. Безопасная проверка `.xlsx`

- Файлы: `src/rasp/imports/excel.py`, `src/rasp/cli.py`, `tests/test_excel_import.py`.
- Приемка: проверяются расширение, ZIP-структура, размеры, обязательные листы и заголовки, формулы, ссылки нагрузки на преподавателей и группы; данные не сохраняются при любой ошибке.
- Проверка: CLI возвращает код `0` для валидного файла и ненулевой код с построчными ошибками для невалидного.

Контрольная точка: можно безопасно принять единый файл с листами `Преподаватели`, `Группы`, `Нагрузка` и получить валидированный пакет данных.

## Этап 1. Импорт и справочники

Результат: пользователь загружает отдельные или объединенные файлы Excel, исправляет ошибки и атомарно обновляет справочники.

### 1.1. Шаблоны и сопоставление колонок

- Пользовательские шаблоны `.xlsx` с примерами и справочниками значений.
- Предпросмотр первых строк и ручное сопоставление нестандартных колонок.
- Сохранение профиля сопоставления для конкретного колледжа.
- Приемка: повторный импорт того же файла идемпотентен по стабильным кодам.

### 1.2. Полный набор исходных данных

- [x] Преподаватели, группы и распределенная нагрузка из объединенного `.xlsx`.
- [x] Специальности: код, название, квалификация, база обучения и форма.
- [x] Версионированные учебные планы по специальности и году набора.
- [x] Дисциплины, ПМ, МДК и практики из учебного плана с семестрами, видами занятий, формами контроля и часами.
- [x] Студенты из Excel: стабильный код, ФИО, группа, статус, период обучения, подгруппы и элективы без лишних персональных данных.
- [ ] Корпуса, аудитории, типы помещений, вместимость и оборудование.
- Контракт полей и проверок: [импорт справочных данных](specs/reference-data-imports.md).
- Приемка: нагрузка не может создать неизвестную дисциплину, а студент — неизвестную группу или подгруппу.

### 1.3. Хранилище

- [x] SQLite для локальной разработки и тестов.
- [x] Версионирование импортов, транзакционная публикация и повторная активация предыдущей версии.
- [x] Приемка: ошибка записи не изменяет активные данные; повторный импорт идемпотентен.
- [ ] PostgreSQL для многопользовательского развертывания.
- [ ] Персистентный журнал отклоненных импортов без сохранения значений ячеек.

### 1.4. Веб-интерфейс импорта

- [x] Загрузка объединенного `.xlsx`, предпросмотр, протокол ошибок и отдельное подтверждение активации.
- [x] История версий и возврат к ранее сохраненной версии.
- [ ] Сопоставление нестандартных колонок и сохранение профилей колледжа.
- [ ] Поиск и редактирование преподавателей, групп, дисциплин, помещений и нагрузки.
- Приемка текущего среза: оператор выполняет стандартный импорт без командной строки.

### 1.5. Проверки дубликатов и целостности

- [x] Дубликаты кодов преподавателей, групп и строк нагрузки внутри файла.
- [x] Ссылки нагрузки на преподавателей и группы, положительные часы и целая длительность события.
- [x] Идемпотентность файла по SHA-256 и атомарная активация версии.
- [x] Дубликаты кодов специальностей, учебных планов и составных ключей дисциплин после нормализации.
- [ ] Совпадение ФИО/названия при разных кодах как предупреждение без автоматического слияния.
- [x] Ссылочная целостность цепочки `специальность → учебный план → дисциплина → нагрузка`.
- [x] Ссылочная целостность цепочки `группа → студент → подгруппа`.
- [x] Единственная применимая редакция учебного плана без пересекающихся активных периодов.
- [x] Сверка часов учебного плана и нагрузки по дисциплине, семестру и виду занятия.
- [x] Запрет членства студента в неизвестной или несовместимой подгруппе.
- [ ] Запрет повторного размещения одной части нагрузки и пересечений группы, подгруппы, студента, преподавателя и аудитории.
- [ ] Отчет с листом, строкой, колонкой, кодом правила и исправлением; ни исходные персональные значения, ни полный путь к файлу не попадают в журнал.
- Приемка: любой блокирующий дефект отменяет пакет целиком; повторная проверка дает тот же нормализованный результат и порядок ошибок.

Контрольная точка: подготовлены и проверены все исходные данные для расчета расписания.

## Этап 2. Календарь и правила колледжа

Результат: администратор настраивает учебный год, смены, звонки, здания и нормативный профиль.

### 2.1. Календарь

- Учебные недели, праздники, практики, сессии, каникулы и исключения.
- Поддержка числителя/знаменателя и произвольных циклов повторения.

### 2.2. Ограничения

- Жесткие: пересечения групп, преподавателей и аудиторий; доступность; вместимость; объем нагрузки; допустимые окна календаря.
- Настраиваемые: дневные и недельные пределы, смены, переходы между корпусами, типы помещений.
- Мягкие: окна, равномерность, предпочтения и компактность расписания.

### 2.3. Проверка готовности

- Отдельный отчет «можно/нельзя запускать расчет» с объяснением каждой блокирующей ошибки.
- Приемка: каждое правило покрыто тестами на границах и может быть связано с источником или локальным положением.

Контрольная точка: исходные данные и правила формируют решаемую задачу без скрытых допущений.

## Этап 3. Генератор расписания MVP

Результат: система строит допустимый вариант и объясняет, почему задача не имеет решения.

### 3.1. Модель решателя

- OR-Tools CP-SAT за изолированным интерфейсом `ScheduleSolver`.
- Фиксированные занятия, связки пар, потоки и подгруппы.
- Детерминированный запуск по seed и сохранение параметров расчета.
- Явные режимы, соответствующие рабочему процессу эталона: черновой расчет наиболее трудных занятий, полный дорасчет и только оптимизация.

### 3.2. Поиск и качество

- Лимит времени, промежуточные решения и отмена расчета.
- Взвешенная целевая функция: окна, равномерность, предпочтения, переходы.
- Метрики качества и сравнение вариантов.
- Повторяемые циклы улучшения: оптимизация качества, затем отдельная оптимизация аудиторий без изменения временной сетки.
- Расшифровка общей оценки по окнам групп/преподавателей, сменам, равномерности, связанным парам, переходам и стабильности варианта.

### 3.3. Диагностика

- Предварительная проверка очевидных противоречий.
- Минимально понятный набор конфликтующих правил и объектов при невозможности расчета.
- Приемка: эталонные синтетические наборы имеют ожидаемый статус и стабильные метрики.
- Контрольный отчёт функционального покрытия показывает, какие операции и результаты уже воспроизводятся системой.

Контрольная точка: для тестового колледжа строится корректное расписание семестра.

## Этап 4. Редактор и рабочий процесс

Результат: диспетчер доводит автоматический вариант до публикации.

- Сетки по группе, преподавателю, аудитории и дню.
- Перетаскивание с мгновенной проверкой конфликтов.
- Блокировка занятий, массовые замены и частичный перерасчет.
- Черновики, версии, сравнение и аудит изменений.
- Приемка: ключевые операции проверены браузерными сценариями и не позволяют незаметно нарушить жесткое правило.

## Этап 5. Публикация и эксплуатация

Результат: расписание доступно сотрудникам и студентам, система готова к резервному копированию и сопровождению.

- Публикация версий и уведомления об изменениях.
- Экспорт в Excel/PDF, печатные формы, календарные представления и API только для чтения.
- Роли администратора, диспетчера и наблюдателя; аудит действий.
- Резервное копирование, восстановление, мониторинг и регламент обновлений.
- Приемка: пройден чек-лист безопасности, восстановление проверено на копии, персональные данные не попадают в логи и публичные артефакты.

## Этап 6. Windows-приложение и установщик

Результат: сотрудник колледжа устанавливает приложение обычным мастером на Windows 10/11 x64 и запускает его без Python и командной строки.

Контрольные точки поставки:

- **Technical alpha EXE** — после импорта корпусов и аудиторий: launcher и внутренний неподписанный installer запускают текущий локальный интерфейс без Python, но автоматический расчёт ещё недоступен.
- **Functional alpha EXE** — после этапов 2 и 3.1: тот же installer включает календарь, проверки готовности и первый `ScheduleSolver`.
- **Production installer** — после редактора, публикации, обновления, подписи и smoke-тестов этапов 4–6.

### 6.1. Desktop launcher

- Запуск единственного экземпляра локального приложения и открытие интерфейса в браузере.
- Привязка сервера только к `127.0.0.1`, выбор свободного порта и понятная диагностика запуска.
- Данные в `%LOCALAPPDATA%\CollegeAutoSchedule`, отдельно от неизменяемых файлов программы.
- Приемка: повторный запуск переводит пользователя в уже работающий экземпляр и не создает вторую запись в базе.

### 6.2. Сборка и установщик

- PyInstaller `onedir`, собираемый на Windows runner с включенными статическими ресурсами.
- Per-user установщик Inno Setup: ярлык меню «Пуск», запись удаления, версия продукта и проверка архитектуры ОС.
- Удаление программы сохраняет пользовательскую базу по умолчанию; полная очистка требует явного выбора.
- Решение: [ADR-001](decisions/001-windows-distribution.md).
- Приемка: приложение устанавливается без Python и без обязательных прав администратора.

### 6.3. Обновление, подпись и выпуск

- Резервная копия перед миграцией схемы, проверяемое обновление с предыдущей поддерживаемой версии и откат при ошибке.
- Authenticode-подпись EXE/установщика для внешнего релиза; ключ подписи доступен только защищенному release job.
- Контрольные суммы артефактов, журнал версий и воспроизводимая привязка сборки к Git commit.
- Smoke-тесты на чистой Windows: установка, первый/повторный запуск, импорт, перезапуск, обновление, удаление и сохранность базы.
- Приемка: финальный установщик не показывает «неизвестный издатель», а обновление не теряет активные версии и историю импортов.

## Непрерывная интеграция и качество

- [x] GitHub Actions запускает тесты на Linux и Windows для каждого push/PR.
- [x] После успешных тестов проверяются зависимости, компиляция Python и сборка wheel со статическими ресурсами.
- [ ] Отдельный ручной/tag workflow собирает Windows launcher и неподписанный внутренний установщик.
- [ ] Release job подписывает и публикует установщик только из защищенной среды после smoke-тестов.
- [ ] Контрактные Excel-тесты покрывают каждый канонический лист и каждую блокирующую проверку.

## Ближайшая итерация

Реализованы доменные модели, безопасное чтение семи листов `.xlsx`, импорт студентов без лишних персональных данных, сверка нагрузки с учебными планами, CLI, SQLite и локальный веб-интерфейс.

Следующий вертикальный срез — **этап 1.2, корпуса и аудитории**:

1. Добавить модели корпуса, аудитории, типа помещения и оборудования.
2. Зафиксировать проверки кодов, вместимости, принадлежности корпусу и совместимости с требованиями нагрузки.
3. Добавить листы помещений в preview/activation-пакет и SQLite.
4. Показать дефициты подходящих аудиторий в отчёте готовности.
5. После этого собрать technical alpha EXE и внутренний Windows installer.

Готовность среза: каждая часть нагрузки имеет допустимые помещения либо явный дефицит; импорт остаётся атомарным, после чего техническая Windows-альфа запускается на чистой системе без Python.
